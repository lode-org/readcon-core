\begin{abstract}
CON is the text geometry that a saddle search stops on.
A resumed search reads the cell, a mask on each Cartesian component, an atom identifier, and, when the frame stores velocities, the time unit of those velocities.
CON 3.1 is a versioned grammar for that text: one JSON header, five fields on each coordinate row, and named sections after the coordinates.
readcon-core is one Rust parser and writer for the grammar, with a C interface for C, C++, Julia and Fortran and a Python binding.
A decimal with no exponent, at most 19 digits and a power of ten from $-22$ to $22$ is converted by Clinger's exact scaling.
Every other spelling goes through an Eisel--Lemire kernel.
On one core of an Intel Xeon, that short path is $1.02$ times faster than the same reader on a file of 160 frames and $1.05$ times faster on a file of 600 frames.
In that interleaved session it is $3.11$ and $3.37$ times faster than an eOn-style C reader of the same files.
In a second session on the same host the short-path reader is faster than ASE 3.29.0 on the CON file and faster than chemfiles 0.10.4, cextxyz and the Python reader in extxyz 0.4.6 on the extended XYZ of the same geometries.
chemfiles returns no velocities.
The eOn-style reader returns coordinates, masses and the cell, and it does not read the mask or the identifier.
\end{abstract}

\noindent\textit{Program title:} readcon-core

\noindent\textit{CPC Library link to program files:} (to be added by the Technical Editor)

\noindent\textit{Licensing provisions:} MIT

\noindent\textit{Supplementary material:} the reserved header keys, the named sections, and the quartiles of every timed read

\textit{Nature of problem:}
A saddle search stops on a geometry file and resumes from it.
The file has to carry the cell, a hold on each Cartesian component, an identifier that survives grouping by chemical type, and the time unit of any velocities.
A reader that drops one of those fields resumes a different calculation.
CON is the text used for this state, and it had no grammar.

\textit{Solution method:}
CON 3.1 puts a JSON object on the second line of a frame.
The object names the major and minor version, the units, the periodic flags and the sections that follow the coordinates.
Each coordinate row holds $x$, $y$, $z$, a three-bit mask and an integer identifier.
The writer prints the shortest decimal that reads back as the same binary64 value.
The reader rounds each decimal to the nearest binary64 value, ties to even.
One Rust core implements the grammar.
C, C++, Julia and Fortran call it through a C interface, and Python calls it through PyO3.
A reader of a known major accepts a later minor, keeps an unknown key, and rejects an unknown major.

\textit{Additional comments including restrictions and unusual features:}
The release measured here is readcon-core 0.18.1.
The short-decimal conversion is a path in the coordinate parser: the comparison build sends every decimal through the Eisel--Lemire kernel instead.
A frame stores geometry and the labels on it.
The history of a quasi-Newton step or of FIRE is outside the frame.
Gzip input is read by every build.
zstd input and a worker pool are build features.

\section{Introduction}
\label{sec:introduction}
Harmonic transition-state theory estimates a rare-event rate from the barrier and from the curvatures at a minimum and at a first-order saddle \cite{eyringActivatedComplexChemical1935,vineyardFrequencyFactorsIsotope1957,hanggiReactionrateTheoryFifty1990}.
The searches that find those points stop on a geometry.
A nudged elastic band resumes from the chain of images \cite{jonssonNudgedElasticBand1998,henkelmanClimbingImageNudged2000,henkelmanImprovedTangentEstimate2000}.
A dimer resumes from two nearby geometries \cite{henkelmanDimerMethodFinding1999}.
Adaptive kinetic Monte Carlo accepts an escape and writes the new state \cite{henkelmanLongTimeScale2001,xuAdaptiveKineticMonte2008,voterExtendingTimeScale2002}.
eOn runs these searches and stops them on a CON file \cite{chillEonSoftwareLong2014,rohitgoswamiTheochemuieonV3602026}.

The file has to return four fields that a trajectory reader can ignore.
A surface search holds the slab, and it can hold one component of an adatom, so the mask belongs to each Cartesian axis.
After the file groups rows by element, a band finds an atom by the identifier stored on the row.
Velocities enter a dynamical step with a unit.
The natural unit of eOn is $(\mathrm{amu}\,\text{\AA}^{2}/\mathrm{eV})^{1/2}$.
With the CODATA 2018 values of the atomic mass constant and the electronvolt, that unit is $\tau=\SI{10.1805}{\femto\second}$ \cite{tiesingaCodataRecommendedValues2021}.
A reader that takes the same numbers as \si{\angstrom\per\femto\second} multiplies the kinetic energy by $(\tau/\mathrm{fs})^{2}=\num{103.643}$.
A restart that repeats the interrupted run reads the coordinates back as the binary64 values that were written \cite{ieeecomputersocietyIeeeStandardFloatingpoint2019}.

Extended XYZ publishes a grammar and keeps extra columns in names that one library chose \cite{kermodeLibatomsExtxyzV0462026,larsenAtomicSimulationEnvironmenta2017}.
The file declares no version and no velocity unit.
H5MD stores identity, velocities and the box in HDF5, and it defines no element for a per-component hold \cite{buylH5mdStructuredEfficient2014}.
POSCAR stores selective-dynamics flags and no atom identifier \cite{kresseEfficiencyAbinitioTotal1996}.
The ASE trajectory keeps the fields in a layout that the Python code of ASE defines.
Of these, none is a versioned grammar for the text eOn already writes.

This paper states that grammar and the parser that implements it.
Section~\ref{sec:frame} reads one frame line by line.
Section~\ref{sec:grammar} states the rules that frame uses.
Section~\ref{sec:parser} is the reader: one core, a boundary walk, and the two conversions of a decimal.
Section~\ref{sec:timings} times that reader against ASE, an eOn-style C reader, chemfiles, cextxyz and the Python reader in extxyz 0.4.6.

The first line is free text.
The writer copies it when it rewrites the frame.
The second line is one JSON object when its first non-blank character is \texttt{\{}, and a frame whose second line is anything else is grammar version 1, the text earlier eOn releases write \cite{brayJavascriptObjectNotation2017}.
The object in the listing names major 3 and minor 1, marks the cell periodic in $x$ and $y$ and open in $z$, lists \texttt{velocities} as the section after the coordinates, and names the units of length, energy, mass and time.

The next two lines are the cell lengths and the cell angles in degrees.
The reader rebuilds the vectors with $\mathbf{a}$ along $x$ and $\mathbf{b}$ in the $xy$ plane \cite{bekkerUnificationBoxShapes1997},
\begin{equation}
\label{eq:cell}
\begin{aligned}
\mathbf{a}&=a\,\hat{\mathbf{x}},\qquad
\mathbf{b}=b\cos\gamma\,\hat{\mathbf{x}}+b\sin\gamma\,\hat{\mathbf{y}},\\
\mathbf{c}&=c\cos\beta\,\hat{\mathbf{x}}+c\,\kappa\,\hat{\mathbf{y}}+c\sqrt{\rho}\,\hat{\mathbf{z}},\\
\kappa&=\frac{\cos\alpha-\cos\beta\cos\gamma}{\sin\gamma},\qquad
\rho=1-\cos^{2}\beta-\kappa^{2}.
\end{aligned}
\end{equation}
A negative $\rho$ is a cell that is not in space.
Orthogonal angles leave a rounding crumb below zero, so a computed $\rho$ in $(-10^{-12},0)$ is stored as a flat cell, $c_z=0$.
Any more negative value is a rejected frame.
When the header carries \texttt{lattice\_vectors}, those nine numbers are the cell and lines 3 and 4 are not.

Two free lines follow the angles.
Then come the number of chemical types, the count of each type and the mass of each type.
Each type is a block: the symbol, a line \texttt{Coordinates of Component} $k$, and one row per atom.
A row holds $x$, $y$, $z$, the mask and the identifier.
A row of four tokens is legal, and the identifier is then the zero-based index of that row in the frame.

From version 2 the mask is the integer
\begin{equation}
\label{eq:mask}
m=b_x+2b_y+4b_z,\qquad b_\alpha\in\{0,1\},
\end{equation}
with $b_\alpha=1$ when component $\alpha$ is fixed.
In the listing the Pt row has mask 7, so every component is fixed, and the H row has mask 4, so only $z$ is fixed.
Version 1 stores 0 for a free atom and 1 for an atom fixed in every component.
Any other token is an illegal flag.
A reader that applies the version-1 rule to the listing rejects the H row.
A reader that applies Eq.~\eqref{eq:mask} to a version-1 file frees $y$ and $z$ of every atom that file held.

The identifier is an integer from 0 through $2^{64}-1$, read as an integer and never through binary64.
The writer refuses a frame that repeats an identifier.
The reader accepts a repeated identifier and keeps the row order.
In the listing the identifiers are 0 and 1 and already match the row order.
Grouping by type permutes that order in a larger file, and sorting by identifier restores it.

A blank line opens the section that the header named.
The velocity block repeats the grouping: a symbol, a heading, and one row of $v_x$, $v_y$, $v_z$, the mask and the identifier.
The unit is the one the header names.
From minor 1 a frame that has a velocity section declares \texttt{units.time}.
Versions 1, 2 and 3.0 are read in the natural unit whatever \texttt{units.time} says, because the producers of those files wrote natural-unit numbers under other labels.
The next line after the frame, if any, is line 1 of the next frame.

\section{The grammar}
\label{sec:grammar}
A CON file is one or more frames and then only white space.
With $T$ types of $N_k$ atoms, a frame is the nine header lines, $T$ coordinate blocks, and the sections named in the header, in that order.
A type count of zero is a frame with no atoms.
The release ships the shape as a parsing expression grammar \cite{fordParsingExpressionGrammars2004}.
Where that grammar admits a token that a numbered clause rejects, the clause decides.

The header of a JSON frame is accepted when the major $M$ is 2 or 3, the minor $\mu$ is a non-negative integer, a major of 3 names \texttt{units.length} and \texttt{units.energy}, and a velocity section at $M=3$, $\mu\ge 1$ names \texttt{units.time}.
A reader accepts a later minor of a known major, copies an unknown key through a rewrite with its digits as read, and rejects any other major.
A section the reader does not know is skipped only when the frame's minor is later than the reader's and \texttt{section\_arity} gives its width.
Each skipped row is counted and not parsed.
Table~\ref{tab:keys} in the supplement lists the reserved keys, and Table~\ref{tab:sections} lists the reserved sections: velocities, forces, energies, charges, spins, magnetic moments, displacements and spreads.

Each finite decimal rounds to the nearest binary64 value, ties to even \cite{clingerHowReadFloating1990,lemireNumberParsingGigabytes2021}.
A spelling of \texttt{nan} or \texttt{inf}, in any case and with any sign, is rejected, as is a decimal that rounds to an infinity.
The default writer prints the shortest decimal that reads back as the same value, through Ry\={u} \cite{steeleHowPrintFloatingpoint1990,adamsRyFastFloattostring2018}.
A caller can ask for a fixed number of digits after the decimal point.
That printing does not round-trip: two values that differed in the last bits can collide.
Gzip and, when the build includes it, zstd are envelopes around the same text \cite{deutschGzipFileFormat1996,colletZstandardCompressionApplicationzstd2021}.
The reader recognises an envelope by its first bytes.

A change to the text either decides a case the earlier text left open, for every version, or adds a requirement under a new minor.
A later minor therefore does not make a reader reject a file that an earlier minor requires it to accept.

\section{The parser}
\label{sec:parser}
readcon-core implements the grammar once, in Rust (Figure~\ref{fig:architecture}).
C, C++ (including eOn), Julia and Fortran call the core through the C interface \cite{bezansonJuliaFreshApproach2017}.
Python calls the core through PyO3 and receives NumPy arrays \cite{harrisArrayProgrammingNumpy2020}.
The public eOn release 3.6.0 links the C++ wrapper \cite{rohitgoswamiTheochemuieonV3602026}.
The layering is the one chemfiles uses: one core, one binding per language \cite{frauxChemfileschemfilesVersion01042023}.

\begin{figure*}[tbp]
\centering
\includegraphics[width=\textwidth]{figures/generated/architecture.pdf}
\caption{One Rust core serves every language.
An arrow runs from the caller to the code it calls.
Python does not pass through the C interface.}
\label{fig:architecture}
\end{figure*}

Figure~\ref{fig:parser} is the read of one file and of one decimal.
The first four bytes select the envelope.
A gzip stream is inflated into memory, and a zstd stream is inflated when the build includes that decoder.
A plain file shorter than \SI{64}{\kibi\byte} is read into memory.
A longer plain file stays mapped for the position-block reader.
The full-frame read measured in Section~\ref{sec:timings} loads the bytes into one buffer on every size.

Frame boundaries are not at fixed offsets.
The start of a frame depends on the type counts and the section list before it, so one thread walks those counts and records the start of each frame.
With one worker, which is the measurement below, that thread then parses the frames in order.
With two or more workers, and a build that includes the pool, each worker parses its own span and the frames come back in file order.
A frame that fails names the line.

\begin{figure*}[tbp]
\centering
\includegraphics[width=\textwidth]{figures/generated/parser.pdf}
\caption{Left: one thread finds the frame starts from the counts, then the frames are parsed in file order.
Right: a short decimal takes Clinger's conversion, and every other spelling takes \texttt{fast\_float2}.
Both paths round to the nearest binary64 value.}
\label{fig:parser}
\end{figure*}

A coordinate row is three decimals, a mask and an optional identifier, scanned once.
The decimal path is the right-hand side of Figure~\ref{fig:parser}.
Clinger's conversion applies when the spelling has no exponent marker, at most 19 digits, a mantissa of at most $2^{53}$, and a power of ten from $-22$ to $22$ \cite{clingerHowReadFloating1990}.
The mantissa is an integer that binary64 represents exactly.
Division or multiplication by the matching power of ten, taken from the same table \texttt{fast\_float2} uses, produces the value.
A sign is applied after the scaling.
Any other spelling, including a decimal with \texttt{e} or \texttt{E}, is parsed by \texttt{fast\_float2}, an Eisel--Lemire kernel \cite{lemireNumberParsingGigabytes2021}.
A non-finite result is rejected on both paths.
The two paths agree bit for bit on the spellings the short path accepts: the short path is the conversion the kernel would have taken before its general case.
The mask is then an integer, 0 or 1 in version 1 and 0 through 7 from version 2, and the identifier is a decimal integer that does not pass through binary64.

The comparison in Section~\ref{sec:fast} changes only that choice.
One build takes the short path.
The other sends every decimal through \texttt{fast\_float2}.
Both are readcon-core 0.18.1, compiled with the same compiler in the release profile.

A path writer writes the frames to a temporary file in the destination directory, flushes that file once the last frame is accepted, and renames it over the destination.
A frame that fails deletes the temporary file, and the destination keeps its earlier bytes.
A writer to a string or to a stream the caller opened writes no temporary file.

\begin{lstlisting}[language=Python,caption={A round trip in Python. The default printer keeps every binary64 value.},label={lst:py}]
import readcon
frames = readcon.read_con("band.con")
readcon.write_con("band.con", frames)
\end{lstlisting}

\section{Readers on one core}
\label{sec:timings}
The geometries are Cu and H in an orthogonal cell, generated in the session.
The masks in these files are only 0 and 7: every fifth atom is fixed in every component, and the others are free.
There is no per-axis hold in the timed files.
The CON files are 24 frames of 36 atoms (\num{30426} bytes), 160 frames of 180 atoms (\num{856362} bytes) and 600 frames of 280 atoms (\num{4933995} bytes).
The extended XYZ files of the same geometries carry positions and velocities and are \num{54507}, \num{1708341} and \num{9787127} bytes.
Every arm ran on one core.
The multi-reader session repeated each read seven times and the tables report the median.

On the CON file, ASE 3.29.0 returns coordinates that match to the last bit, and it returns the atoms of mask 7 as fixed in every component.
It returns no identifier.
The header of these files names no periodicity, which the grammar reads as periodic in all three directions, and ASE marks every direction open.
The eOn-style reader is a C loop in the shape of the eOn coordinate reader: nine header lines, then a symbol, a component line and one coordinate line per atom, with \texttt{sscanf} of three doubles.
The trailing mask and identifier are not stored.
Coordinates, masses and the cell match to the last bit.
The reader does not read a velocity block.

On the extended XYZ file, cextxyz and the Python reader in extxyz 0.4.6 return positions and velocities that match to the last bit, and they return the orthogonal cell.
chemfiles 0.10.4 returns no velocities.
Its positions differ from the written values by at most $\num{5.6e-17}$, $\num{4.4e-16}$ and $\num{1.8e-15}$\,\si{\angstrom} on the three files.
On the smallest file the cell lengths differ by $\num{1.8e-15}$ and $\num{3.6e-15}$, one and two units in the last place, because the lengths are rebuilt from the lattice matrix.
Those three losses are why the chemfiles bars in Figure~\ref{fig:timings} are hatched.
The extended XYZ file is a different text: it is larger, it stores velocities on every row, and it has no mask and no identifier.
The times on the right of the figure are the cost of that file, not a ratio against the CON file.

In this session the short-decimal reader is faster than every other arm on every size.
Against the eOn-style reader the ratios are $2.53$, $4.65$ and $4.89$.
Against ASE they are $37.9$, $37.1$ and $35.3$.
Against cextxyz they are $22.5$, $34.3$ and $35.4$, and against the Python extxyz reader $95.9$, $76.6$ and $70.5$.
The absolute times are not the same in the next session.

\subsection{The short decimal}
\label{sec:fast}
The fast-path session interleaves the two readcon builds and the eOn-style reader on the two larger CON files.
One round is the Eisel--Lemire build, the eOn reader, the short-decimal build, the short-decimal build, the eOn reader, and the Eisel--Lemire build.
Four rounds give eight samples of each arm.
A ratio is reported when the interquartile ranges do not overlap.
Figure~\ref{fig:fast} is that session.

On the 160-frame file the medians are \SI{2.90}{\milli\second} without the short path, \SI{2.84}{\milli\second} with it, and \SI{8.83}{\milli\second} for the eOn-style reader.
On the 600-frame file they are \SI{16.3}{\milli\second}, \SI{15.5}{\milli\second} and \SI{52.3}{\milli\second}.
The short path is $1.02$ and $1.05$ times the other readcon build.
It is $3.11$ and $3.37$ times the eOn-style reader.
The ranges do not overlap on either file, so both ratios stand.
The gain over the other readcon build is small.
The gain over the C reader is the larger part of the difference, and it is already present in the build that sends every decimal through Eisel--Lemire: that build is $3.04$ and $3.21$ times the eOn reader in the same session.

The same 160-frame file took \SI{1.88}{\milli\second} in the multi-reader session and \SI{2.84}{\milli\second} here.
The 600-frame file took \SI{10.5}{\milli\second} and \SI{15.5}{\milli\second}.
The eOn-style reader stayed at \SI{8.74}{\milli\second} and \SI{8.83}{\milli\second}, and at \SI{51.2}{\milli\second} and \SI{52.3}{\milli\second}.
The ratio against that reader is $4.65$ and $4.89$ in the first session and $3.11$ and $3.37$ in the second, because the readcon time moved and the C reader's time did not.
The comparison that cancels a drift through the round is the interleaved one.

\section{Conclusions}
\label{sec:conclusions}
CON 3.1 is a versioned grammar for the geometry a saddle search resumes from.
The second line names the version, the units and the sections.
Each coordinate row carries a three-bit mask and an identifier, and a velocity section from minor 1 names its time unit.
readcon-core parses that text once, and every language binding calls that parse.
A short decimal takes Clinger's exact scaling, and every other spelling takes an Eisel--Lemire kernel.
On the files measured here the short path is $1.02$ and $1.05$ times the reader without it.
The same reader is $3.11$ and $3.37$ times an eOn-style C reader in the interleaved session, and faster than ASE, chemfiles, cextxyz and the Python extxyz reader in the other session.
The losses are on the other side of the comparison and in the absolute times.
chemfiles drops the velocities and misses the cell lengths by one or two units in the last place.
ASE returns no identifier and no periodic direction.
The eOn-style reader does not store the mask or the identifier.
The readcon time on one file is \SI{1.88}{\milli\second} in one session and \SI{2.84}{\milli\second} in the other.

The timings were taken on one core of an Intel Xeon with 8 cores and \SI{47}{\gibi\byte} of memory.
readcon-core 0.18.1 was compiled with rustc 1.88.0 in the release profile, once with the short-decimal path and once without it.
The eOn-style reader was compiled with gcc 13.3.0 at \texttt{-O3}.
ASE 3.29.0, chemfiles 0.10.4, extxyz 0.4.6 and NumPy 2.5.4 ran under Python 3.12.3, with one thread.
