\title{readcon-core: a specification-aware reader and writer for the CON
checkpoint format with a language-neutral C ABI}

\input{authors.tex}

\begin{abstract}
Rare-event and saddle-search codes in the eOn family write atomic
checkpoints as \texttt{.con} and \texttt{.convel} text
\cite{chillEONSoftwareLong2014}. The historical layout is a nine-line
header plus type-grouped atom blocks. Independent readers treat
column~4 as a boolean and do not parse declared force sections, the
pre-grouping atom index, or a units object. This paper records CON
versions~2 and~3 (JSON metadata on line~2, a spec-aware constraint
bitmask, declared sections, required units in v3) and describes
\texttt{readcon-core}, the reference implementation. The library is an
hourglass: a Rust core, a C ABI (\texttt{rkr\_*}) published as
\texttt{include/readcon-core.h}, and wrappers for C++, Python, Julia,
and Fortran. Chemfiles
\cite{frauxChemfiles2023} is an optional ingress path; the measured
mapping is XYZ into the same \texttt{ConFrame}. Instruction-count
measurements (Valgrind Cachegrind) and equal-geometry wall timings
against ASE \cite{larsenAtomicSimulationEnvironment2017}, chemfiles,
MDAnalysis H5MD
\cite{michaudAgrawalMDAnalysisToolkit2011,gowersMDAnalysisPythonPackage2016},
and raw h5py are reported with host provenance. Text CON remains the
on-disk authority; gzip and optional zstd compress that text; a
Cap'n Proto schema is an RPC wire, not a binary file format.
\end{abstract}

\begin{keyword}
CON \sep convel \sep rare-event dynamics \sep checkpoint format
\sep FFI \sep chemfiles \sep H5MD
\end{keyword}

\end{frontmatter}

* Introduction
:PROPERTIES:
:CUSTOM_ID: sec:introduction
:END:

Saddle searches, adaptive kinetic Monte Carlo, and nudged elastic
band calculations checkpoint atomic configurations many times per
image. The eOn =.con= file is that checkpoint
\cite{chillEONSoftwareLong2014}: a short header, then atoms grouped
by chemical type, each line a position, a constraint flag, and a
fifth integer that historical writers used as a display index.
Velocities were conventionally stored in a sibling =.convel=
file. Later practice added force blocks and free-form comments on
line 2.

The format is small and human-readable. Independent implementations
have treated column 4 as ``fixed or not'' and have ignored line 2.
ASE's =ase.io.eon= reader is of that class
\cite{larsenAtomicSimulationEnvironment2017}: it decodes column 4
with =bool(int(...))=, discards column 5, and treats leftover
force-section lines after the coordinate parse as an error.
Archived eOn C++ does the same boolean decode while keeping the
fifth integer on =.con= (not on =.convel=). Neither
stack has a units object. Column 4 therefore cannot carry a per-axis
mask unless the reader consults a spec version.

=readcon-core= is the reference reader and writer for that
contract. Versions 2 and 3 are defined in the accompanying
specification (=docs/orgmode/spec.org=); this paper states the
parts that matter for interchange. The design goal is one on-disk
checkpoint and one C ABI, so a Fortran optimizer, a C++ driver, and
a Python notebook see the same constraints, identities, and
metadata.

* Related work
:PROPERTIES:
:CUSTOM_ID: sec:related
:END:

CON is a rare-event checkpoint, not a general structure archive and
not an MD analysis tape. The nine-line type-grouped layout is the
unversioned eOn de facto format. Chill et al. describe the eOn
software and do not specify atom-line columns
\cite{chillEONSoftwareLong2014}.

Extended XYZ puts ~Lattice=~ and a
~Properties=~ column schema on the comment line; lean XYZ has
neither. There is no journal specification of extXYZ; the living
grammar is the ASE/libAtoms dialect
\cite{larsenAtomicSimulationEnvironment2017}. CON uses a JSON object
on line 2 for the same job (machine metadata on a line that old
tools treat as a comment) and keeps a first-class three-bit
constraint mask and a pre-grouping =atom_id=. Lean XYZ, as
timed in this paper, has no constraint mask. The library's ASE
adapters convert a parsed =ConFrame= to =Atoms= and
back; they do not register a =format='con'= plugin and do
not replace =ase.io.eon=. That reader treats leftover
force-section lines after the coordinate parse as an error.

H5MD is the structured particle container in this journal
\cite{deBuylH5MDStructuredEfficient2014}. It can carry per-particle
mass, force, velocity, SI unit attributes, and an observables tree.
It has no first-class per-axis freeze mask and no type-grouped
atom-index recovery. The equal-geometry timings below treat H5MD as
a peer load path, not as ``MD tape.'' GROMACS XTC/TRR and CHARMM/NAMD
DCD are engine tapes: masses and restraints live in the TPR or PSF,
and restart is a separate checkpoint (=cpt=,
=namdbin=) \cite{abrahamGromacsHighPerformance2015}. They are
cited here and are not timed.

LAMMPS =dump custom= can store ids and optional forces on one
row \cite{thompsonLammpsFlexibleSimulation2022}. It does not store a
spec-versioned constraint bitmask and does not require type-grouped
blocks. Atomsk converts among many crystal and MD formats and does
not read or write eOn CON \cite{hirelAtomskToolManipulating2015}.
chemfiles is the optional ingress library
\cite{frauxChemfiles2023}: it opens many formats; this paper
measures XYZ\(\to\)\texttt{ConFrame}. MDAnalysis is used only as the
H5MD Python API in the wall-time table
\cite{michaudAgrawalMDAnalysisToolkit2011,gowersMDAnalysisPythonPackage2016};
MDTraj is not timed \cite{mcgibbonMDTrajModernOpen2015}.
An optional metatensor export copies four \texttt{TensorBlock}s
(positions, velocities, forces, per-atom energies)
\cite{bigiMetatensorMetatomicFoundational2026}; it is not a
TensorMap or metatomic \texttt{System} path.

* The CON format
:PROPERTIES:
:CUSTOM_ID: sec:format
:END:

A spec 2 file places a JSON object on line 2 with at least
=con_spec_version=. Spec 3 requires a =units= object
with non-empty =length= and =energy= keys. The
=sections= array names the data blocks that follow the
coordinates (velocities, forces, energies, charges, spins, magnetic
moments). The Rust writer fills =sections= from the frame.

Column 4 is a bitmask $0\ldots 7$. Historical writers emit $0$ or
$1$ (free or all-fixed). This specification assigns a three-bit
mask for spec 2+: \(1\) is \(x\)-only and \(7\) is all-fixed. Writers
emit $7$ for all-fixed, never $1$. The decoder is spec-aware so
that a legacy file with $1$ remains all-fixed. Old readers that
test ``nonzero means fixed'' over-constrain $y$ and $z$ on a legal
spec 2 file whose mask is $1$--$6$; they still freeze the atom.
Column 5 is =atom_id=. Readers accept four-column lines and
default the missing index to the sequential position in the frame.

Line 2 was chosen because existing tools treat it as a comment.
Adding a tenth header line, overwriting the postbox on lines 5--6, or
shipping a sidecar =.con.meta= would break those parsers or
lose pairing.

Velocities may live in a declared =sections= entry on a
=.con= file. The =.convel= extension is the historical
name and the blank-separator fallback when the =sections= key
is absent. A present key, including an empty array, disables that
fallback.

Gzip is the portable compression. zstd is an optional feature with
the same magic-byte detection. Both decompress to text and then
parse. They are not a new format.

A Cap'n Proto schema (=schema/ReadCon.capnp=) exists for an
optional Rust RPC service. It is a parsed-frame encoding over TCP or
a Unix domain socket. It is not UCX, ADIOS, or an on-disk ``bcon''
authority. The campaign store =readcon-db= keeps cooked SoA
numerics in LMDB (RCSO) as a derived cache. Text CON remains the
file that independent tools must implement.

* Library architecture
:PROPERTIES:
:CUSTOM_ID: sec:architecture
:END:

The crate is an hourglass. The Rust core owns =ConFrame=, the
writer, and optional chemfiles import. An optional Pest grammar
(=grammar/readcon.pest=) is a surface-syntax companion; the
I/O hot path is the hand-written parser. The C ABI in
=src/ffi.rs= is generated into =include/readcon-core.h=
and that header is what CMake FetchContent, the Meson wrap-file, and
=pkg-config= install. Consumers do not run cbindgen.

Python (=readcon= / =readcon-chemfiles=), Julia, and
Fortran bind the C ABI (Python also calls the Rust parser directly).
The =python= feature enables Rayon. Then
=read_all_frames= / =read_con= parse in parallel
when the buffer is at least $48$\,KiB; =n_threads=1= forces
the sequential iterator. A default =cargo build= is
sequential. The published C prefix is built with =parallel=,
so =rkr_read_all_frames= follows the same automatic
policy. =rkr_read_all_frames_n_threads= selects the
worker count ($0$ auto, $1$ sequential, $n\geq 2$ a pool). Lean
builds return =RKR_STATUS_FEATURE_DISABLED= for
chemfiles, metatensor, and CUDA rather than hiding the symbol. RPC
is a Rust feature and is not on the C ABI. Builder
=rkr_frame_builder_build= returns =NULL= on
validation errors (including type-mass mismatch); it does not abort.

The 0.14.x contract freezes ownership, sentinels (=NaN=,
\texttt{UINT64\_MAX}, \texttt{NULL}), and the Z \(=1\ldots 92\) (+ D/T)
helpers. Additive symbols may appear in a 0.14.z patch. A breaking C
change is a 0.15+ minor.

* Performance

:CUSTOM_ID: sec:performance

Two measurements are kept separate.

Valgrind Cachegrind on =examples/cachegrind_harness.rs= is
the commit-stable instruction-count measurement.
Table \ref{tab:cachegrind} reports selected rows from the
committed table
(=docs/source/_generated/cachegrind_results.rst=,

On this identical-frame concatenation, =CON.gz= (gzip of the
text CON) is $0.86\times$ the positions-only H5MD file and
=CON.zst= is $0.065\times$. Those sizes are for this blob,
not a general rare-event law. h5py is faster because it loads a
coordinate array. MDAnalysis H5MD cost is the Python API
\cite{gowersMDAnalysisPythonPackage2016}. Chemfiles ingress is a
different payload: lean XYZ has no constraint mask
\cite{frauxChemfiles2023}. The table reports them together so the
payloads stay visible.

The three native CON medians are =readcon.read_con= (or
=read_con_string=) under =python,chemfiles=. That
feature set enables Rayon. The $1.68$\,MB concat is above
=PARALLEL_BYTES_THRESHOLD= ($48$\,KiB). Those rows are the
automatic policy, not =n_threads=1=, and they include
=PyConFrame= conversion. Table \ref{tab:io} is a different
protocol: the Rust program
=examples/wall_scale_harness.rs= on the same 100-frame
payload, no Python.

* Multi-language fidelity
:PROPERTIES:
:CUSTOM_ID: sec:fidelity
:END:

A clause-keyed Phase A corpus under
=resources/conformance/= locks the column-4 collision (spec 1
value $1$ is all-fixed; spec 2 value $1$ is $x$-only; spec 2
value $7$ is all-fixed), required v3 units, missing
=con_spec_version=, unsupported version $4$, unknown
section names, and =validate=true= without
=sections=. Each valid id has a JSON golden for spec
version, column-4 mask, positions, atom ids, and symbols. Rust, the
C ABI, and Python share the same parser. Fortran and Julia call the
C ABI. The optional Pest grammar is exercised separately
(=cargo test --features grammar=).
The published cxx tarball on the =v0.14.8= GitHub Release is
the CMake FetchContent URL (SHA256
=5ae875b90faef98102949c9c0ec03d34ffab9ba5bdc8386c70e42cc153fcbd4e=).

* Applications
:PROPERTIES:
:CUSTOM_ID: sec:applications
:END:

eOn and the amsel campaign stack consume CON as the checkpoint
between potential evaluations and saddle searches.
=readcon-db= indexes those files for energy, formula, and
section presence.
Table \ref{tab:fair-campaign} is the committed companion freeze
on the same =tiny_cuh2.con= ladder ($N=10$, $50$, $100$, $200$,
$500$) in both stores. That table is companion appendix
material. It is not a main-claim parse timing.

=resources/examples/neb_band.con= is a four-image spec-3
band (two atoms). =resources/examples/cuh2_band.con= is the same
declared bead tags on the 218-atom =cuh2.con= geometry.
Each frame declares =neb_bead=, =neb_band=,
=energy=, =fmax=.
=scripts/print_neb_band.py=,
=examples/print_neb_band.cpp=, and
=examples/print_neb_band.f90= print bead, energy, and
$f_{\max}$. Table \ref{tab:neb} is that output for the two-atom
file. The energies are line-2 JSON. They are not a production NEB.
The declared barrier $E_1-E_0$ is $\nebBarrierEv$\,eV. The declared
$f_{\max}$ is not recomputed from the force block.
Python =index_projection()= returns the same campaign scalars
(formula, energy, =neb_bead=) that =readcon-db= indexes.
=scripts/run_cpc_vignette.sh= prints the two-atom band, checks
=neb_band.tsv=, and, when =readcon-db= is on =PATH=, ingests the
file and selects =neb_bead= 0--3.

Python notebooks use =readcon= for lean I/O and
=readcon-chemfiles= when the input arrives as XYZ.
