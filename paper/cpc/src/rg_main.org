\begin{abstract}
Saddle-point and rare-event searches are often stopped and resumed, sometimes in a different code from the one that started them.
The geometry file used for the restart then has to keep the per-component atomic constraints, the atom identifiers, the time unit of the velocities and the binary64 coordinates.
CON is a text geometry format used in eOn, ASE and other codes, and it has had no specification.
Here, we describe CON 3.1, a versioned grammar that formalizes and extends CON, and readcon-core, its reference reader and writer.
A JSON header on the second line of each frame declares the grammar version and the physical units, each coordinate row stores a three-bit constraint mask and an atom identifier, and a reader of a given major version accepts later minor revisions.
Two conformance corpora of \corpusFiles{} legal and illegal files fix what a conforming reader returns, and every Python and C read path in readcon-core returns the verdict of every corpus file.
On a platinum slab, a climbing-image band resumed from CON 3.1 reproduces the uninterrupted band exactly, whereas dropping the height constraint of the adatom changes the prefactor by a factor of \sigfig{2}{\eFivePrefactorRatioFree}.
A borrowed DLPack view of \dlpackAtoms{} atomic positions costs \dlpackRatio{} times an explicit copy.
\end{abstract}

\textit{Nature of problem:} Rare-event campaigns stop saddle searches and resume them from a stored geometry, often on another machine or in another code.
A resumed surface search needs the Cartesian components that each atom holds fixed, since a held component removes a mode from the harmonic prefactor and can move the saddle.
It also needs the identifier on each row, by which events and band images are matched, and the time unit of the velocities, since a misread unit scales the kinetic energy by the square of the conversion factor.
A restart that repeats the interrupted run to roundoff must further read back the binary64 coordinates as they were written.
Of the formats in common use, H5MD defines no mask element, the POSCAR structure file defines no atom identifier, and extended XYZ keeps both in column names chosen by one library and names no time unit.
CON had no specification, so each reader decided for itself which files are legal and what each column means.

\textit{Solution method:} CON 3.1 is a versioned grammar that formalizes and extends the CON text, and readcon-core is its reference reader and writer.
The second line of a frame is a JSON object that declares the major and minor version, the units, the periodic flags and the per-atom sections that follow the coordinates.
The fourth column of a coordinate row is a three-bit mask of the fixed components, and the fifth is an atom identifier.
From minor 1 onward, a velocity section declares its time unit.
A reader of a known major accepts any later minor, keeps unknown keys and skips a section of a later minor by its declared width.
The writer prints the shortest decimal that reads back as the same binary64 value.
Two corpora of legal and illegal files fix the verdict of a conforming reader on the clauses of the specification.
readcon-core implements the grammar once in Rust, with a C interface for C++, Julia and Fortran and a PyO3 binding for Python, and a writer given a path replaces the destination only after the last frame has been accepted.

\textit{Additional comments including restrictions and unusual features:} This paper describes readcon-core~\readconCargoVersion{} (Data availability).
Every build reads gzip input, while zstd input and parallel parsing are build features, both enabled in the Python wheel.
A frame stores Cartesian coordinates, the cell, the periodic flags, the mask, one identifier per atom, and optional per-atom velocities, forces, energies, charges, spins, magnetic moments, displacements and spreads.
It stores no optimizer history, so an optimizer with memory takes a different path after a restart.
Files written by earlier eOn releases are grammar version 1 and are read as such.
Velocities in a file of an earlier version are read in the natural time unit of eOn, whatever time unit the file names.
In Python, \texttt{readcon.read\_con(path)} returns the frames of a file (Listing~\ref{lst:py}).

\textit{References:} eOn \cite{chillEonSoftwareLong2014,rohitgoswamiTheochemuieonV3602026}; readcon-core releases \cite{goswamiReadconcoreConConvel2026}.

\section{Introduction}\label{sec:introduction} Transition state theory \cite{eyringActivatedComplexChemical1935,vineyardFrequencyFactorsIsotope1957,hanggiReactionrateTheoryFifty1990} reduces the kinetics of an activated process to its saddle points and the vibrations about them.
The nudged elastic band \cite{jonssonNudgedElasticBand1998,henkelmanClimbingImageNudged2000,henkelmanImprovedTangentEstimate2000,asgeirssonNudgedElasticBand2021}, minimum-mode following methods \cite{henkelmanDimerMethodFinding1999,kastnerSuperlinearlyConvergingDimer2008,olsenComparisonMethodsFinding2004,goswamiGaussianProcessSaddle2025} and string methods \cite{eStringMethodStudy2002,petersGrowingStringMethod2004} locate those saddle points.
Adaptive kinetic Monte Carlo (AKMC) chains such searches into state-to-state trajectories, and together with accelerated molecular dynamics it reaches milliseconds and longer \cite{henkelmanLongTimeScale2001,xuAdaptiveKineticMonte2008,voterExtendingTimeScale2002,perezLongtimeDynamicsThrough2016,chillEonSoftwareLong2014}.
A long-timescale run in eOn \cite{chillEonSoftwareLong2014,rohitgoswamiTheochemuieonV3602026} spawns thousands of saddle searches, often on volunteer or distributed resources \cite{andersonBoincSystemPublicresource2004,pedersenDistributedImplementationAdaptive2010}, and their geometries pass between Python drivers \cite{larsenAtomicSimulationEnvironmenta2017,hermesSellaOpensourceAutomationfriendly2022}, C++ engines and Fortran electronic structure codes \cite{kresseEfficiencyAbinitioTotal1996}.
A search that stops on one machine resumes on another from a geometry file, and that file is the checkpoint of the search.

Such a checkpoint has to return four fields that a trajectory reader can ignore.
Mobility belongs to each Cartesian component, and when a surface search holds an adatom at a set height while the adatom crosses the surface, losing that hold changes the saddle the search converges to (Section~\ref{sec:prefactor}).
Mode following and the bookkeeping of AKMC match atoms across frames and events by an identifier on each row, so a reader has to return that identifier as written rather than the row order.
Dynamical steps read velocities, and since the natural time unit of eOn is \((\mathrm{amu}\,\text{\AA}^2/\mathrm{eV})^{1/2}=\wkTimeFs\,\mathrm{fs}\), a reader that takes the same numbers as \(\text{\AA}/\mathrm{fs}\) scales the kinetic energy by \(\velFactorSq\).
Finally, a restart that repeats the interrupted run to roundoff has to read back the binary64 coordinates \cite{ieeecomputersocietyIeeeStandardFloatingpoint2019}, which requires a writer that prints the shortest decimal that reads back as the same double \cite{steeleHowPrintFloatingpoint1990,adamsRyFastFloattostring2018} and a reader that rounds each decimal to the nearest double \cite{clingerHowReadFloating1990}.
Two readers given the same bytes then return the same fields only under a versioned grammar, not under the conventions of one reader.

Existing formats keep some of these fields, but none keeps all four in places that its own specification defines.
Extended XYZ adds key-value metadata to the comment line of the plain Cartesian coordinate format (XYZ) and publishes a grammar \cite{kermodeLibatomsExtxyzV0462026}, yet the writer of the Atomic Simulation Environment (ASE) keeps the mask in a \texttt{move\_mask} column \cite{aseSource3290}, identifiers live only in a column whose name each writer chooses, and no standard key gives a format version or a velocity unit.
H5MD \cite{buylH5mdStructuredEfficient2014,folkOverviewHdf5Technology2011} stores particle identifiers, velocities and the box in HDF5, with units through an optional module, but it defines no element for a per-component constraint.
The compressed (XTC) and full-precision (TRR) trajectories of GROMACS \cite{gromacsFileFormats2026}, with velocities in \(\mathrm{nm}/\mathrm{ps}\) \cite{gromacsDefinitionsUnits2026}, the binary trajectory (DCD) format of CHARMM, NAMD and X-PLOR, with optional fixed-atom and unit-cell records \cite{vmdDcdPlugin2026}, and the trajectory next generation (TNG) format \cite{spangbergTrajectoryNgPortable2011,lundborgEfficientExtensibleFormat2014} define no per-component mask.
The Amber NetCDF convention declares a unit for every variable, the velocities included, but it defines neither an atom identifier nor a constraint \cite{amberNetcdfConvention2022}.
POSCAR, the structure file of the Vienna Ab initio Simulation Package \cite{vaspwikiPoscar2026,kresseEfficiencyAbinitioTotal1996}, stores selective-dynamics flags along each lattice vector but no atom identifier, and the ASE trajectory keeps every field in a layout defined by the Python code of ASE.
Chemfiles \cite{frauxChemfileschemfilesVersion01042023}, MDAnalysis \cite{michaudAgrawalMDAnalysisToolkit2011,gowersMdanalysisPythonPackage2016}, the Open Visualization Tool (OVITO) \cite{stukowskiVisualizationAnalysisAtomistic2010} and Open Babel \cite{oboyleOpenBabelOpen2011} read and write many of these formats.
None of these four opens a version-1 CON file or a CON 3.1 file, while the eon module of ASE opens both but stops at the velocity section of the frame of Section~\ref{sec:worked} \cite{aseSource3290}.
The transition-state library TSASE, from the group that wrote eOn, writes CON with six decimals and one fixed flag per atom, and its reader ignores the identifier column and makes every cell periodic \cite{terrellTsaseTransitionStateLibrary2025}.

Here, we describe CON 3.1, which formalizes the CON format and extends it, and readcon-core, its reference implementation.
CON 3.1 adds a JSON header line that declares the format version, the physical units and the periodic flags, stores a three-bit constraint mask and an atom identifier on each coordinate row, allows declared per-atom sections, and reads each coordinate back as the binary64 value that was written.
readcon-core is one Rust core with C, C++, Python, Julia and Fortran interfaces, similar in layout to chemfiles \cite{frauxChemfileschemfilesVersion01042023}, and it provides borrowed DLPack views of the positions (Section~\ref{sec:dlpack}).
We compare its read times with those of ASE, MDAnalysis, OVITO, pymatgen and pure Python (Section~\ref{sec:performance}).
Of the formats in this comparison, only CON 3.1 specifies all four checkpoint fields, and readcon-core is the only one of these readers that returns the constraint mask, the atom identifier and the velocity time unit from fields its own specification defines, while accepting later minor revisions.

The header line is one JSON object \cite{brayJavascriptObjectNotation2017}, recognized by its first non-blank character, \texttt{\{}, and a frame whose header is anything else is grammar version~1, the text written by earlier eOn releases.
In Listing~\ref{lst:frame} the object names the major and minor version of the grammar, declares the slab periodic in \(x\) and \(y\) and open in \(z\), lists \texttt{velocities} as the only section after the coordinates, and gives the units of length, energy, mass and time.

The two cell lines carry the lengths \(a=b\approx\wkLengthA\,\text{\AA}\) and \(c=\wkLengthC\,\text{\AA}\) and the angles \(\alpha\), \(\beta\) and \(\gamma\) in degrees.
From these the reader rebuilds the cell \cite{bekkerUnificationBoxShapes1997} with \(\mathbf{a}\) along \(x\) and \(\mathbf{b}\) in the \(xy\) plane, the restricted triclinic form of LAMMPS \cite{lammpsHowtoTriclinic2026},
\begin{equation}
\label{eq:cell}
\begin{aligned}
\mathbf{a}&=a\,\hat{\mathbf{x}},\qquad
\mathbf{b}=b\cos\gamma\,\hat{\mathbf{x}}+b\sin\gamma\,\hat{\mathbf{y}},\\
\mathbf{c}&=c\cos\beta\,\hat{\mathbf{x}}+c\,\kappa\,\hat{\mathbf{y}}+c\sqrt{\rho}\,\hat{\mathbf{z}},\\
\kappa&=\frac{\cos\alpha-\cos\beta\cos\gamma}{\sin\gamma},\qquad \rho=1-\cos^2\beta-\kappa^2.
\end{aligned}
\end{equation}
In binary64 the cosine of the double nearest \(\pi/2\) is \(\num{\wkCosRight}\), so for this cell Eq.~\eqref{eq:cell} gives \(b_x=\num{\wkBx}\,\text{\AA}\) and \(c_x=c_y=\num{\wkCxy}\,\text{\AA}\).
ASE~\wkAseVersion{} instead returns \(b_x=\wkAseRightBx\), since it sets to zero the cosine of any angle within two units in the last place of a right angle \cite{aseSource3290}.

Whether three angles describe a cell at all depends on the radicand \(\rho\).
The volume of the cell of Eq.~\eqref{eq:cell} is \(V=a\cdot b\sin\gamma\cdot c\sqrt{\rho}\), and \(V^2\) is the determinant of the Gram matrix \(G\) of the three vectors, so that
\begin{equation}
\label{eq:gram}
\begin{aligned}
\rho\,\sin^2\gamma = D &= 1-\cos^2\alpha-\cos^2\beta-\cos^2\gamma+2\cos\alpha\cos\beta\cos\gamma,\\
\det G &= a^2b^2c^2D .
\end{aligned}
\end{equation}
No three vectors in space have angles with \(D<0\), and \(D=0\) is a flat cell.
For angles of \(\wkFlatAlpha\), \(\wkFlatBeta\) and \(\wkFlatGamma\) degrees the exact \(\rho\) is zero, since \(\mathbf{c}\) then lies in the plane of \(\mathbf{a}\) and \(\mathbf{b}\), while binary64 gives \(\hat\rho=\num{\wkFlatRadicand}\).
readcon-core accepts that frame with \(c_z=0\), because \(\hat\rho\) lies inside the window of \(\num{\wkWindow}\) that Section~\ref{sec:format} allows for the roundoff of a zero radicand, whereas ASE stops on its own assertion that \(\hat\rho\ge0\).

After two free lines and the counts of types, atoms and masses, each type has a block with its symbol, a label, and one row per atom of \(x\), \(y\), \(z\), the mask and the identifier.
For a frame of major \(M\), with \(M=1\) when the header is not JSON, the mask is the integer
\begin{equation}
\label{eq:mask}
m =
\begin{cases}
b_x + 2 b_y + 4 b_z, & M\ge 2,\\
b_x = b_y = b_z, & M = 1,
\end{cases}
\qquad b_\alpha\in\{0,1\},
\end{equation}
with \(b_\alpha=1\) when component \(\alpha\) is fixed.
In Listing~\ref{lst:frame} the bottom rows are fixed in every component, the top layer is free, and the adatom is held in \(z\) alone.
A reader that applies the version-1 rule of Table~\ref*{tab:clauses} to this frame rejects the mask of the adatom as an illegal flag, and a reader that applies the CON 3.1 rule to a version-1 file frees \(y\) and \(z\) of every atom held there.

The identifier is the index of the atom in the numbering of the writer, from \wkIdFirst{} on the first row to \wkIdLast{} on the last, so sorting by identifier undoes the permutation that grouping the atoms by type introduced.
A reader returns the identifiers exactly and in file order, up to \(2^{64}-1\), and a row without an identifier takes its zero-based position in the frame.

The blank line~\wkLineBlank{} opens the velocity section declared in the header, which repeats the shape of the coordinate block with one row of \(v_x\), \(v_y\), \(v_z\), mask and identifier per atom.
The held atoms have zero velocity and the adatom has \(v_z=0\), so \wkMovingAtoms{} atoms move.
The velocities are in the unit named in the header, the natural unit of eOn,
\begin{equation}
\label{eq:tau}
\tau=\left(\frac{m_{\mathrm{u}}\,\text{\AA}^{2}}{\mathrm{eV}}\right)^{1/2}
=\left(\frac{1.6605\times10^{-27}\,\mathrm{kg}\cdot 10^{-20}\,\mathrm{m}^{2}}{1.6022\times10^{-19}\,\mathrm{J}}\right)^{1/2}
\approx\wkTimeFs\,\mathrm{fs},
\end{equation}
with the CODATA 2018 values of the atomic mass constant \(m_{\mathrm{u}}\) and the electronvolt \cite{tiesingaCodataRecommendedValues2021}.
In that unit the frame has a kinetic energy \(\tfrac{1}{2}\sum_i m_i\lvert\mathbf{v}_i\rvert^2\) of \(\wkKinetic\,\mathrm{eV}\).
A reader that takes the same numbers as \(\text{\AA}/\mathrm{fs}\) returns \(\wkKineticMisread\,\mathrm{eV}\), which is larger by \((\tau/\mathrm{fs})^2=\velFactorSq\).

The coordinates are printed in the shortest form that reads back as the same binary64 value \cite{steeleHowPrintFloatingpoint1990,adamsRyFastFloattostring2018}, in Listing~\ref{lst:frame} with \wkDigitsMin{} to \wkDigitsMax{} significant digits, and the reader rounds each decimal to the nearest binary64 value \cite{clingerHowReadFloating1990,lemireNumberParsingGigabytes2021}.
Section~\ref{sec:cases} gives what a writer of six decimals does to a resumed band.
Listing~\ref*{lst:testrun} of the supplementary material runs the example program of the release on this file and on the two variants of the angle line.

\section{The grammar of CON 3.1}\label{sec:format} The normative specification, with \clauseTotal{} numbered clauses, is Section~\ref*{sec:spec-normative} of the supplementary material, and Table~\ref*{tab:clauses} there maps the rules used in Section~\ref{sec:worked} to their clauses.
Each clause carries a requirement word, such as MUST, SHOULD or MAY, with the meaning that the IETF gives these words \cite{bradnerKeyWordsUse1997}.
A CON file is one or more frames with no marker between them, followed only by lines of white space.
With \(T\) atom types of \(N_k\) atoms each, a frame \(\mathcal{F}\) is
\begin{equation}
\label{eq:frame}
\begin{aligned}
\mathcal{F}&\to \lambda_1\ \ \lambda_2\ \ (a\ b\ c)\ \ (\alpha\ \beta\ \gamma)\ \ \lambda_5\ \ \lambda_6\ \ T\ \ (N_1\cdots N_T)\\
&\qquad (M_1\cdots M_T)\ \ \mathcal{B}_1\cdots\mathcal{B}_T\ \ \mathcal{S}^{*},\\
\mathcal{B}_k&\to s_k\ \ (\text{\texttt{Coordinates of Component}}\ k)\ \ \bigl(x\ y\ z\ m\ [\iota]\bigr)^{N_k},\\
\mathcal{S}&\to \varnothing\ \ \mathcal{V}_1\cdots\mathcal{V}_T,\\
\mathcal{V}_k&\to s_k\ \ (S\ \text{\texttt{of Component}}\ k)\ \ \bigl(v_1\cdots v_w\ m\ \iota\bigr)^{N_k},
\end{aligned}
\end{equation}
where each symbol or parenthesized group is one line, a superscript repeats a line, \(\lambda_1\), \(\lambda_5\) and \(\lambda_6\) are free lines, \(\lambda_2\) is the header, \(M_k\) and \(s_k\) are the mass and symbol of type \(k\), \(\iota\) is the identifier, \(\varnothing\) is a blank line and \(S\) is the name of a section of width \(w\).
A type count of zero gives a frame without atoms.
The release also ships this shape as an informative parsing expression grammar (PEG) \cite{fordParsingExpressionGrammars2004}, and where the PEG admits a token that a clause rejects, the clause decides.

The cell rule rests on Eq.~\eqref{eq:gram}.
readcon-core evaluates Eq.~\eqref{eq:cell} in binary64 and accepts the angles when the computed radicand satisfies \(\hat\rho>-\num{\wkWindow}\), setting \(c_z=0\) when such a \(\hat\rho\) is negative, and otherwise it rejects the frame with a validation error.
Since the window is fixed, a cell whose exact radicand lies between \(-\num{\wkWindow}\) and zero is accepted as flat, and every set of angles that misses a real cell by more is rejected.
The readcon-core writer refuses a frame that repeats an identifier, and no clause ties the identifiers of one frame to those of another.

Each number is a finite decimal that the reader rounds to the nearest binary64 value, with ties to even \cite{ieeecomputersocietyIeeeStandardFloatingpoint2019,clingerHowReadFloating1990,lemireNumberParsingGigabytes2021}.
By default the writer prints the shortest decimal that rounds back to the same value \cite{steeleHowPrintFloatingpoint1990,loitschPrintingFloatingpointNumbers2010,andryscoPrintingFloatingpointNumbers2016,adamsRyFastFloattostring2018}, so a frame that is written and read back has every coordinate unchanged, and an option prints six fixed decimals instead.
A gzip or zstd envelope wraps the same text \cite{deutschGzipFileFormat1996,colletZstandardCompressionApplicationzstd2021}, and the reader recognizes it by its content; readcon-core decodes zstd when built with that feature and otherwise refuses the file with an error that names zstd.

Table~\ref{tab:keys} lists the reserved keys of the JSON line.
The major version is \texttt{con\_spec\_version}, and the minor version is \texttt{con\_spec\_minor}, which is zero when absent.
For a frame whose header is a JSON object, let \(\mu\) be its minor, \(U\) the set of keys of its \texttt{units} object, and \(V\) true when the frame has a velocity section.
The reader accepts that header only when
\begin{equation}
\label{eq:version}
\begin{aligned}
&M\in\{2,3\}\ \wedge\ \mu\in\mathbb{N}\\
&\wedge\ \bigl(M=3\Rightarrow\{\mathrm{length},\mathrm{energy}\}\subseteq U\bigr)\\
&\wedge\ \bigl(M=3\wedge\mu\ge1\wedge V\Rightarrow \mathrm{time}\in U\bigr).
\end{aligned}
\end{equation}
For \(M=3\) it also rejects a unit whose dimension does not match its quantity.
A reader accepts a later minor of a known major, keeps an unknown key on rewrite with its digits as read, and rejects any other major as an unsupported version, which is the meaning that H5MD gives to its own pair of major and minor numbers \cite{buylH5mdStructuredEfficient2014}.

From minor 1 onward, a frame with a velocity section declares \texttt{units.time}, and the reader converts that unit to femtoseconds by Eq.~\eqref{eq:tau}.

Each accepted specification change includes corpus tests.

Algorithm~\ref{alg:parser} is the path reader of readcon-core~\readconCargoVersion{}.
Without an explicit count of two or more threads it parses on the calling thread.
A plain file up to a fixed size is read whole, into memory below \(B_{\mathrm{map}}=\wkMmapBytes\) bytes and memory-mapped from there on, and a longer plain file is parsed from a window of a few mebibytes that moves through the text, so the text is never resident beside every finished frame.
A gzip or zstd file is inflated into one buffer and parsed frame after frame.
With \(P\ge2\) threads the reader holds the whole text, finds the frame boundaries in one thread, since the start of each frame depends on the counts before it, then parses the frames in a pool of \(P\) threads and returns them in file order.
Table~\ref*{tab:anchors} of the supplementary material gives the source lines of each step.

One frame of \(N\) atoms costs \(\Theta(N)\) time and memory.
For a text of \(B\) bytes, after inflation for a gzip or zstd file, the read costs a \(\Theta(B)\) parse, which a pool of \(P\) threads shares after one serial \(\Theta(B)\) boundary walk, and the frames it returns occupy \(\Theta(B)\) memory.
A compressed file of \(C\) bytes is first inflated in \(\Theta(C+B)\) time.
Figure~\ref*{fig:memory} of the supplementary material shows the peak resident set that each read adds.

Every writer that takes a path writes its frames to a temporary file in the directory of the destination, and once the last frame is accepted, it flushes and syncs that file and renames it over the destination.
A frame that fails deletes the temporary file, and the destination keeps its earlier bytes.
The uncompressed writers of the C interface write a device or a named pipe in place, and a writer to a string or to a stream that the caller opened writes no temporary file.
Each language binding has a test that fails a write midway and compares the destination with its earlier bytes, and Listing~\ref{lst:py} reads a band from Python and writes it back to the same path, after which the file contains either its earlier frames or the frames written.

\begin{lstlisting}[language=Python,caption={\textbf{A checkpoint round trip in Python.} The default printer keeps every binary64 value; six decimals are a separate argument.},label={lst:py}]
import readcon
frames = readcon.read_con("band.con")
readcon.write_con("band.con", frames)
\end{lstlisting}

\section{Tensor exchange through DLPack}\label{sec:dlpack} A caller that already holds a frame reads its coordinates as a tensor without a copy, through DLPack \cite{dlpackDLPack2026}.
On the Rust builder, the methods for positions, velocities, forces, per-atom energies and masses return a borrowed float64 tensor, and the method for atom identifiers returns a borrowed uint64 tensor, each of which lives as long as the builder and sits on the CPU in the default build.
A C caller that needs the tensor after the builder is gone takes the versioned managed tensor, and that export copies the storage.
Python materializes a contiguous NumPy array, which implements the DLPack protocol, so PyTorch and JAX take the array without a second copy, whereas CuPy accepts only device memory and needs one copy from the host.
An optional Cargo feature, off by default, also exports a frame to metatensor from Rust, from the C header and from the Fortran wrappers, and Python and Julia have no binding for that feature \cite{bigiMetatensorMetatomicFoundational2026}.

The measured exchange is a Rust program that calls \texttt{positions\_dlpack} on a \texttt{ConFrameBuilder} of \dlpackAtoms{} copper atoms and either sums the borrowed view in place or copies it into an owned buffer and sums the copy, in six repeats of each arm.
The view takes a median of \dlpackViewUs{} microseconds and the copy a median of \dlpackCopyUs{} microseconds, so the view costs \dlpackRatio{} times the copy.
A 95 percent bootstrap interval for that ratio, drawn from those six samples, is \dlpackRatioLo{} to \dlpackRatioHi{}, and the interval excludes 1.
The type 7 interquartile ranges are \dlpackViewIqr{} microseconds and \dlpackCopyIqr{} microseconds, and Figure~\ref*{fig:dlpack} of the supplementary material shows the six repeats.

\section{Conformance}\label{sec:conformance} A specification settles a dispute between readers only when each reader can be tested against it, as JSONTestSuite did for JSON parsers with files that a parser must accept, must reject, or may treat as implementation-defined \cite{seriotParsingJsonMinefield2016}.
The conformance corpus of readcon-core contains \(\corpusConfValid\) legal and \(\corpusConfInvalid\) illegal files (Table~\ref{tab:corpus} of the supplementary material), and its manifest names the error class of each illegal file.
Read through the Python module, all \(\corpusConfAgree\) files return the verdict and error class of their manifest entries, and the release checks the same files from Rust, Python, C, Fortran and Julia.

That corpus has few files for the header, the sections and the units, so we wrote a second corpus of \(\cthreeoneFiles\) CON 3.1 files, \(\cthreeoneAccepted\) legal and \(\cthreeoneRejected\) illegal.
For each file, its manifest names the clauses that decide it and the outcome, which is the frame count and periodic flags of a legal file or the error class and line of an illegal one.
For \(\cthreeoneExplicit\) entries the outcome follows from the text of a clause, and the others record a reading where the text leaves the case open (Section~\ref*{sec:supp-corpus31}).
All \(\cthreeoneMatch\) files return the outcome of their entry at one, two and eight threads and at the default.
Both corpora also go through every read path of the Python module and the C library, in the serial C library build and the parallel build at each of those thread counts, and all \(\cpathsReads\) reads return the outcome that the manifests name (Table~\ref*{tab:corpus-paths}).

We also wrote an independent reader in \(\corpusIndepLines\) lines of Python that import nothing from readcon.
It follows the clauses of the specification, and where a clause requires a rejection without naming its class, or no clause decides a case, it follows the reading of the corpus manifest.
On all \(\corpusIndepAgree\) of the \(\corpusFiles\) files of both corpora, the frame list and the frame iterator of readcon and the independent reader each return the manifest outcome.
On the \(\corpusBoth\) files that both readers accept, all \(\corpusFieldIdentical\) carry the same bits in every coordinate, velocity and cell entry and equal masks, identifiers, units and periodic flags (Table~\ref*{tab:corpus-crosscheck}).
As in differential testing \cite{mckeemanDifferentialTestingSoftware1998}, the two readers also read \(\mutantCases\) mutants of the \(\mutantFiles\) corpus files under \(\mutantMaxBytes\) bytes, \(\mutantPerSeed\) from each of \(\mutantSeeds\) seeds, each of which inserts, deletes or replaces characters and tokens at one to three random places.
The readers agree on \(\mutantSame\) of them, with the same frame count or error class.
The other \(\mutantDiffer\) all fall in one case that no clause decides, a JSON number on line 2 beyond the binary64 range, which the independent reader rejects anywhere on that line and readcon-core accepts in a key that is not reserved.
A variant of the independent reader that follows readcon-core on that case returns the readcon-core verdict on all of them.
Of the \(\clauseTotal\) clauses of the specification, \(\clauseCovered\) are named by a corpus file, a probe or a test of the library, and eleven of the other \(\clauseUncovered\) bind a reader, all of which Section~\ref*{sec:supp-corpus31} lists.

One name must mean one language for every reader that carries it.
The published wheels of readcon-core 0.17.0, 0.17.1, 0.17.2 and \rcDriftFourth{} do not return the same outcome on every probe file.
On files of two frames whose first line is empty, the oldest refuses the file and the later three read two frames, and on a blank symbol line the newest two refuse a file that the earlier two read (Section~\ref*{sec:supp-versions}).
Each of those changes decided a case that the text of its release left open, and Table~\ref*{tab:versions} lists the clauses involved.

\subsection{The mask and the prefactor}\label{sec:prefactor} A barrier is one number, but the harmonic prefactor needs the free modes at the saddle.
In harmonic transition state theory the rate is \(k=\nu\exp(-\Delta E^\ddagger/k_{\mathrm{B}}T)\) with the Vineyard prefactor \cite{vineyardFrequencyFactorsIsotope1957}
\begin{equation}
\label{eq:vineyard}
\nu=\frac{\prod_{i=1}^{n}\nu_i^{\mathrm{min}}}{\prod_{i=1}^{n-1}\nu_i^{\ddagger}},
\end{equation}
where the products run over the \(n\) free modes of the minimum and the \(n-1\) real modes of the saddle, so a mask that frees one more component adds a mode to each product and can also move the saddle itself.
We wrote the endpoints of the same slab through each route and read them back before relaxing them under the constraints that the reader returns, then converged a climbing-image band with the fast inertial relaxation engine (FIRE) \cite{bitzekStructuralRelaxationMade2006} and took the Hessian of the highest image, after Newton steps on the free coordinates brought the endpoints to their minima and that image, where it has one imaginary mode, to its saddle.
With the height held, the barrier is \(\eFiveBarrierHeld\,\mathrm{eV}\) on a path of \(\eFivePathHeld\,\text{\AA}\).
The highest image has \(\eFiveModesHeld\) free modes, one imaginary mode of \(\eFiveImagHeld\,\mathrm{meV}\) with \(\eFiveWeightHeld\) of its weight on the lateral motion of the adatom, and a prefactor of \(\num{\eFivePrefactorHeldNum}\,\mathrm{Hz}\), which CON 3.1, the ASE trajectory, FixScaled POSCAR and h5py H5MD all return (Table~\ref{tab:prefactor-routes}).
With the height free, which is the problem a reader solves when the file has lost the hold, the band crosses a saddle at \(\eFiveBarrierFree\,\mathrm{eV}\) with \(\eFiveModesFree\) free modes and a prefactor of \(\num{\eFivePrefactorFreeNum}\,\mathrm{Hz}\), \sigfig{2}{\eFivePrefactorRatioFree} times the held value.

IRA shape matching \cite{gundeIRAShapeMatching2021} instead pairs the atoms of each element by geometry, with a Hausdorff distance of \(2.11\,\text{\AA}\), and not by bonds.

\FloatBarrier \section{Discussion}\label{sec:discussion}
Most atomistic formats have no specification apart from the code that reads them, so that code is the de facto definition of the format, and two readers of one file agree only as far as their authors copied each other.
Other fields have fixed their interchange files in published texts.
Crystallography did so with the Crystallographic Information File (CIF) \cite{hallCrystallographicInformationFile1991,bernsteinSpecificationCrystallographicInformation2016}.
In particle physics, the Les Houches event file passes parton-level events from matrix-element generators to general-purpose generators \cite{Alwall2007LHEF}, the second SUSY Les Houches Accord passes spectra and decay tables between spectrum calculators, decay codes and event generators \cite{Allanach2009SLHA2}, and the HepMC3 library defines the event record that generators hand to analysis \cite{Buckley2021HepMC3}.
Electronic structure has done the same for densities and wavefunctions with the European Theoretical Spectroscopy Facility (ETSF) file format \cite{Gonze2008ETSF} and TREXIO \cite{posenitskiyTrexioFileFormat2023}, and for pseudopotentials with the pseudopotential markup language (PSML) \cite{Garcia2018PSML}.
A computed barrier can be reproduced from a file only when every reader returns the same fields from it, and a versioned specification together with a corpus of files of known verdicts turns that condition into a test that any reader can run.

CON 3.1 takes that route for the saddle-search checkpoint.
H5MD and extended XYZ are the nearest formats, and the h5py and ASE routes of Section~\ref{sec:cases} carry all four fields through a convention added on top of each, but that convention lives in one reader again.
The drift between published readcon-core wheels in Section~\ref{sec:conformance} is the same failure inside one project, and the corpus and the version rule of Eq.~\eqref{eq:version} contain it, since every case that a release decides enters the text and the corpus, and a later minor never makes a reader reject a file that an earlier minor requires it to accept.
The cost is a text format, whose file sizes and read times Figure~\ref{fig:pareto} sets beside those of the binary formats, and readcon-db keeps a shuffled, compressed cache for campaigns where storage matters.

\section{Conclusions}\label{sec:conclusions}
A resumed saddle search repeats an interrupted run only when the checkpoint keeps the per-component constraints, the atom identifiers, the time unit of the velocities and the binary64 coordinates as written.
We have formalized and extended the CON format as the versioned CON 3.1 grammar and implemented it in readcon-core, one Rust core behind C, C++, Python, Julia and Fortran interfaces, with borrowed DLPack views of the coordinates.
Every Python and C read path of readcon-core returns the verdict of the corpus manifests on all \corpusFiles{} legal and illegal files of the two conformance corpora.
On the held Pt(100) slab, a band resumed from CON 3.1 repeats the uninterrupted band bit for bit, and a reader that drops the hold sends the band to a saddle whose prefactor is \sigfig{2}{\eFivePrefactorRatioFree} times larger.
The specification and the conformance corpus of CON 3.1 belong to no single simulation engine, so any program can test its reader against the corpus, add a section under a later minor without breaking older readers, and resume a search from the files of another code.
