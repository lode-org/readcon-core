checkpoint format with a language-neutral C ABI}

\author[ui]{Rohit Goswami}

\begin{abstract}
Rare-event and saddle-search codes in the eOn family write atomic
checkpoints as \texttt{.con} and \texttt{.convel} text
\cite{chillEONSoftwareLong2014}. The historical layout is a nine-line
header plus type-grouped atom blocks. Independent readers treat
column~4 as a boolean and do not parse declared force sections, the
pre-grouping atom index, or a units object. This paper records CON
versions~2 and~3 (JSON metadata on line~2, a spec-aware constraint
bitmask, declared sections, required units in v3) and describes
\texttt{readcon-core}, the reference implementation. The library is an
hourglass: a Rust core, a C ABI (\texttt{rkr\_*}) published as
\texttt{include/readcon-core.h}, and wrappers for C++, Python, Julia,
and Fortran. Chemfiles
\cite{frauxChemfiles2023} is an optional ingress path; the measured
mapping is XYZ into the same \texttt{ConFrame}. Instruction-count
measurements (Valgrind Cachegrind) and equal-geometry wall timings
against ASE \cite{larsenAtomicSimulationEnvironment2017}, chemfiles,
MDAnalysis H5MD
\cite{michaudAgrawalMDAnalysisToolkit2011,gowersMDAnalysisPythonPackage2016},
and raw h5py are reported with host provenance. Text CON remains the
on-disk authority; gzip and optional zstd compress that text; a
Cap'n Proto schema is an RPC wire, not a binary file format.
\end{abstract}

\section{Introduction}

Saddle searches, adaptive kinetic Monte Carlo, and nudged elastic
band calculations checkpoint atomic configurations many times per
image. The eOn \texttt{.con} file is that checkpoint
\cite{chillEONSoftwareLong2014}: a short header, then atoms grouped
by chemical type, each line a position, a constraint flag, and a
fifth integer that historical writers used as a display index.
Velocities were conventionally stored in a sibling \texttt{.convel}
file. Later practice added force blocks and free-form comments on
line~2.

The format is small and human-readable. Independent implementations
have treated column~4 as ``fixed or not'' and have ignored line~2.
ASE's \texttt{ase.io.eon} reader is of that class
\cite{larsenAtomicSimulationEnvironment2017}: it decodes column~4
with \texttt{bool(int(...))}, discards column~5, and does not parse
force sections. Archived eOn C++ does the same boolean decode while
keeping the fifth integer on \texttt{.con} (not on \texttt{.convel}).
Neither stack has a units object. Column~4 therefore cannot carry a
per-axis mask unless the reader consults a spec version.

\texttt{readcon-core} is the reference reader and writer for that
contract. Versions~2 and~3 are defined in the accompanying
specification (\texttt{docs/orgmode/spec.org}); this paper states the
parts that matter for interchange. The design goal is one on-disk
checkpoint and one C ABI, so a Fortran optimizer, a C++ driver, and
a Python notebook see the same constraints, identities, and
metadata.

\section{Related work}

CON is a rare-event checkpoint, not a general structure archive and
not an MD analysis tape. The nine-line type-grouped layout is the
unversioned eOn de facto format. Chill et al.\ describe the eOn
software and do not specify atom-line columns
\cite{chillEONSoftwareLong2014}.

Extended XYZ puts \texttt{Lattice=} and a
\texttt{Properties=} column schema on the comment line; lean XYZ has
neither. There is no journal specification of extXYZ; the living
grammar is the ASE/libAtoms dialect
\cite{larsenAtomicSimulationEnvironment2017}. CON uses a JSON object
on line~2 for the same job (machine metadata on a line that old
tools treat as a comment) and keeps a first-class three-bit
constraint mask and a pre-grouping \texttt{atom\_id}. Lean XYZ, as
timed in this paper, has no constraint mask.

H5MD is the structured particle container in this journal
\cite{deBuylH5MDStructuredEfficient2014}. It can carry per-particle
mass, force, velocity, SI unit attributes, and an observables tree.
It has no first-class per-axis freeze mask and no type-grouped
atom-index recovery. The equal-geometry timings below treat H5MD as
a peer load path, not as ``MD tape.'' GROMACS XTC/TRR and CHARMM/NAMD
DCD are engine tapes: masses and restraints live in the TPR or PSF,
and restart is a separate checkpoint (\texttt{cpt},
\texttt{namdbin}) \cite{abrahamGromacsHighPerformance2015}. They are
cited here and are not timed.

LAMMPS \texttt{dump custom} can store ids and optional forces on one
row \cite{thompsonLammpsFlexibleSimulation2022}. It does not store a
spec-versioned constraint bitmask and does not require type-grouped
blocks. Atomsk converts among many crystal and MD formats and does
not read or write eOn CON \cite{hirelAtomskToolManipulating2015}.
chemfiles is the optional ingress library
\cite{frauxChemfiles2023}: it opens many formats; this paper
measures XYZ$\to$\texttt{ConFrame}. MDAnalysis is used only as the
H5MD Python API in the wall-time table
\cite{michaudAgrawalMDAnalysisToolkit2011,gowersMDAnalysisPythonPackage2016}.
An optional metatensor export copies four \texttt{TensorBlock}s
(positions, velocities, forces, per-atom energies)
\cite{bigiMetatensorMetatomicFoundational2026}; it is not a
TensorMap or metatomic \texttt{System} path.

\section{The CON format}

A spec~2 file places a JSON object on line~2 with at least
\texttt{con\_spec\_version}. Spec~3 requires a \texttt{units} object
with non-empty \texttt{length} and \texttt{energy} keys. The
\texttt{sections} array names the data blocks that follow the
coordinates (velocities, forces, energies, charges, spins, magnetic
moments). The Rust writer fills \texttt{sections} from the frame.

Column~4 is a bitmask $0\ldots 7$. Historical writers emit $0$ or
$1$ (free or all-fixed). This specification assigns a three-bit
mask for spec~2+: $1$ is $x$-only and $7$ is all-fixed. The decoder
is spec-aware so that a legacy file with $1$ remains all-fixed. Old
readers that test ``nonzero means fixed'' over-constrain $y$ and $z$
on a legal spec~2 file whose mask is $1$--$6$; they still freeze the
atom.

Line~2 was chosen because existing tools treat it as a comment.
Adding a tenth header line, overwriting the postbox on lines 5--6, or
shipping a sidecar \texttt{.con.meta} would break those parsers or
lose pairing.

Velocities may live in a declared \texttt{sections} entry on a
\texttt{.con} file. The \texttt{.convel} extension is the historical
name and the blank-separator fallback when the \texttt{sections} key
is absent.

Gzip is the portable compression. zstd is an optional feature with
the same magic-byte detection. Both decompress to text and then
parse. They are not a new format.

A Cap'n Proto schema (\texttt{schema/ReadCon.capnp}) exists for an
optional Rust RPC service. It is a parsed-frame transport. It is not
an on-disk ``bcon'' authority. The campaign store
\texttt{readcon-db} keeps cooked SoA numerics in LMDB (RCSO) as a
derived cache. Text CON remains the file that independent tools must
implement.

\section{Library architecture}

The crate is an hourglass. The Rust core owns \texttt{ConFrame}, the
writer, and optional chemfiles import. An optional Pest grammar
(\texttt{grammar/readcon.pest}) is a surface-syntax companion; the
I/O hot path is the hand-written parser. The C ABI in
\texttt{src/ffi.rs} is generated into \texttt{include/readcon-core.h}
and that header is what CMake FetchContent, the Meson wrap-file, and
\texttt{pkg-config} install. Consumers do not run cbindgen.

Python (\texttt{readcon} / \texttt{readcon-chemfiles}), Julia, and
Fortran bind the C ABI (Python also calls the Rust parser directly).
Lean builds return \texttt{RKR\_STATUS\_FEATURE\_DISABLED} for
chemfiles, metatensor, and CUDA rather than hiding the symbol. RPC
is a Rust feature and is not on the C ABI. Builder
\texttt{rkr\_frame\_builder\_build} returns \texttt{NULL} on
validation errors (including type-mass mismatch); it does not abort.

The 0.14.x contract freezes ownership, sentinels (\texttt{NaN},
\texttt{UINT64\_MAX}, \texttt{NULL}), and the Z~$=1\ldots 92$ (+ D/T)
helpers. Additive symbols may appear in a 0.14.z patch. A breaking C
change is a 0.15+ minor.

\section{Multi-language fidelity}

A clause-keyed Phase~A corpus under
\texttt{resources/conformance/} locks the column-4 collision (spec~1
value~$1$ is all-fixed; spec~2 value~$1$ is $x$-only; spec~2
value~$7$ is all-fixed), required v3 units, missing
\texttt{con\_spec\_version}, unsupported version~$4$, unknown
section names, and \texttt{validate=true} without
\texttt{sections}. Rust, the C ABI, and Python share the same
parser. Fortran and Julia call the C ABI. The optional Pest grammar
is exercised separately (\texttt{cargo test --features grammar}).
The published cxx tarball on the \texttt{v0.14.7} GitHub Release is
the CMake FetchContent URL (SHA256
\texttt{14710ec007b2131d2c0e13931bf3e7e443ce87627ace2fb21497a05ea0b5df43}).

\section{Applications}

eOn and the amsel campaign stack consume CON as the checkpoint
between potential evaluations and saddle searches.
\texttt{readcon-db} indexes those files for energy, formula, and
section presence. \texttt{resources/examples/neb\_band.con} is a
three-image band with \texttt{neb\_bead}, \texttt{energy}, and
forces; \texttt{scripts/print\_neb\_band.py} prints energy versus
bead. Python notebooks use \texttt{readcon} for lean I/O and
\texttt{readcon-chemfiles} when the input arrives as XYZ.
\texttt{read\_chemfiles} also accepts PDB and GRO through chemfiles;
those paths are untested in this tree and do not preserve residues
or occupancy. The C++ RAII header is the path for in-process drivers
that cannot embed a Python interpreter.
